### 2026-10-17
- Project started. Coordination repo `haiku-rpi`. The `haiku-pi/haiku` and `haiku-pi/buildtools`
  forks have `origin` = fork and `upstream` = review.haiku-os.org; our work is on branch `rpi4` of `haiku`.
- Host: Haiku build prerequisites installed, jam built; arm64 cross toolchain (gcc, binutils from
  buildtools) built in `sources/haiku/generated.arm64`.
- **H1 ✅** `jam -q @minimum-mmc` (hrev60262) builds; the image boots to the **Tracker desktop on
  QEMU virt** (EDK2, 4 CPUs, ramfb) in < 100 s. `scripts/qemu-virt.sh` saves a screenshot.
  - Finding: with **virtio-blk-pci** the boot reaches userland, then block I/O stalls ("vnode not
    becoming unbusy") and every later read fails with an I/O error, on 1 and 4 CPUs alike.
    **virtio-blk-device (MMIO)** is clean. PCI interrupt delivery on arm64 is the suspect; this matters

### 2026-10-18 (night)
- **Flash lane proven**: netboot Linux → `wget | dd` 352 MB in 14 s → read-back SHA-256 match in 8 s,
  fully unattended (`sd-cycle.sh --flash`). The other project agreed we may overwrite the card;
  `restore-peer-sd.sh` puts their release image back.
- **H2 ✅ H3 ✅ on the real Pi 4 (4 GB, rev 0xc03111)**: firmware → U-Boot → `haiku_loader.efi` → kernel on
  **4 CPUs** → `PANIC: did not find any boot partitions!` → `kdebug>`, on UART and HDMI (Haiku boot
  splash + KDL on the EFI framebuffer). U-Boot hands over ~6 s before the panic; the ~58 s before it
  is the Pi's netboot attempt with no DHCP server.
- Upstream bugs found and fixed on `rpi4` (all generic, all needed for any EL2/U-Boot/clock-controller board):
  1. loader: a UART whose registers are not page aligned (BCM2835 mini UART +0x40) → "Too many levels at mapping" panic;
  2. loader: `_arch_transition_EL2_EL1` overwrote TTBR0/MAIR/VBAR_EL1 with EL2 values after they were
     programmed → secondaries released from the spin table ran with TTBR0 = 0 (stuck in
     `smp_cpu_rendezvous`); the boot CPU ran on U-Boot's MAIR;
  3. loader: spin-table release write + secondary data not cleaned to PoC (secondaries poll with caches off);
  4. loader: UART baud programmed from an unknown clock (-1) → keep firmware setup;
  5. PL011: the constructor's loopback test left IBRD=1/LCRH=0 (5-bit words) → garbage on real HW;
  6. FDT bus: `get_reg()` ignored parent `ranges` (all Pi peripherals sit behind /soc, emmc2bus, /scb).
- Found with QEMU raspi4b + QMP register dumps + gdbstub (`scripts/qemu-raspi.sh --gdbserver`), each fix
  then confirmed on hardware. QEMU ignores baud/word-length and caches: (4), (5), (3) were found by reading
  code for "what QEMU cannot show" before the first HW cycle.

### 2026-10-18 (01:45)
- **H4 progress — Haiku mounts its boot volume from the Pi's SD card** (`Mounted boot partition:
  /dev/disk/mmc/0/1`), userland starts. New/changed on `rpi4`:
  - `sdhci`: FDT attachment for `brcm,bcm2711-emmc2`; 32-bit-only register access (`NarrowRegister`,
    transfer mode + command in one store); base clock from the VideoCore (new `generic/bcm2835_mailbox`
    module: **mailbox works first try**, 100 MHz); DMA window 0xC0000000/1 GiB from `dma-ranges` (new
    FDT `get_dma_window()`); cache maintenance for the non-coherent controller (new arm64 dcache helpers);
    PIO fallback when there is no SDMA.
  - Upstream bugs fixed: **W1C interrupt status acknowledged with `|=`** (lost "transfer complete" →
    first read hung forever); timeout-clock field mask 5→6 bits; card scanned twice; divider rounding;
    trace macro that broke an if/else; MMC debug tracing on by default (60+ s of serial spam per boot).
  - kernel: wait up to 10 s for a late boot device (SD/USB) instead of panicking; arm64 user exceptions
    got an uninitialized signal → now classified and logged; **CNTKCTL_EL1 never set on the EL2 path**
    → launch_daemon trapped on `mrs cntvct_el0` (EC 0x18; same bug Phoenix had).
- **QEMU raspi4b reaches the Haiku desktop** booting from SD through the emmc2 driver (DTB patched so
  QEMU's SD controller looks like emmc2; PIO, since QEMU's model has no SDMA). Colours R/B swapped.
- On the real Pi: with SDMA userland stalls silently right after launch_daemon starts; with PIO
  (forced, experiment) registrar/package_daemon/net_server run but app_server never draws.
  Linux and Phoenix both use **ADMA2** on this controller ("no in-tree driver uses SDMA on BCM2711").
- Bench: card **read-back lane** (`sd-cycle.sh --read-back`, 400 MB in 11 s via `dd | nc`) +
  `sd-syslog.sh` (host `bfs_shell`); `--send` types into the UART at given times; new kernel feature
  **serial emergency keys** (3× Ctrl-] + d → KDL) to inspect a stalled system.
