## Progress

### 2026-10-17
- Project started. Coordination repo `haiku-rpi`. The `haiku-pi/haiku` and `haiku-pi/buildtools`
  forks have `origin` = fork and `upstream` = review.haiku-os.org; our work is on branch `rpi4` of `haiku`.
- Host: Haiku build prerequisites installed, jam built; arm64 cross toolchain (gcc, binutils from
  buildtools) built in `sources/haiku/generated.arm64`.
- **H1 ✅** `jam -q @minimum-mmc` (hrev60262) builds; the image boots to the **Tracker desktop on
  QEMU virt** (EDK2, 4 CPUs, ramfb) in < 100 s. `scripts/qemu-virt.sh` saves a screenshot.
  - Finding: with **virtio-blk-pci** the boot reaches userland, then block I/O stalls ("vnode not
    becoming unbusy") and every later read fails with an I/O error, on 1 and 4 CPUs alike.
    **virtio-blk-device (MMIO)** is clean. PCI interrupt delivery on arm64 is the suspect; this matters
    later for the Pi's PCIe USB controller (H6).
- U-Boot `rpi_4_defconfig` built (`sources/u-boot`). Pi firmware pinned (`scripts/fetch-pi-firmware.sh`).
- Bench: flash lane (Linux netboot initramfs that writes + SHA-verifies the SD card), `sd-cycle.sh`,
  UART capture, HDMI snapshots, shared bench lock with the other project on this host. The card may be
  overwritten (agreed with the other project); `scripts/restore-peer-sd.sh` puts their image back.
