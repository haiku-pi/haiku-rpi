  is the Pi's netboot attempt with no DHCP server.
- Upstream bugs found and fixed on `rpi4` (all generic, all needed for any EL2/U-Boot/clock-controller board):
  1. loader: a UART whose registers are not page aligned (BCM2835 mini UART +0x40) → "Too many levels at mapping" panic;
  2. loader: `_arch_transition_EL2_EL1` overwrote TTBR0/MAIR/VBAR_EL1 with EL2 values after they were
     programmed → secondaries released from the spin table ran with TTBR0 = 0 (stuck in
     `smp_cpu_rendezvous`); the boot CPU ran on U-Boot's MAIR;
  3. loader: spin-table release write + secondary data not cleaned to PoC (secondaries poll with caches off);
  4. loader: UART baud programmed from an unknown clock (-1) → keep firmware setup;
  5. PL011: the constructor's loopback test left IBRD=1/LCRH=0 (5-bit words) → garbage on real HW;
  6. FDT bus: `get_reg()` ignored parent `ranges` (all Pi peripherals sit behind /soc, emmc2bus, /scb).
- Found with QEMU raspi4b + QMP register dumps + gdbstub (`scripts/qemu-raspi.sh --gdbserver`), each fix
  then confirmed on hardware. QEMU ignores baud/word-length and caches: (4), (5), (3) were found by reading
  code for "what QEMU cannot show" before the first HW cycle.

### 2026-10-18 (02:45) — intermittent boot freeze (open)
- `boot-bench.sh` results: ADMA2 2/3 desktop; next 3 trials 0/3; **SMP disabled 2/3** → not SMP-only.
- Every freeze hits a burst of SD I/O (packagefs mount, launch_daemon start) and is *hard*: the serial
  emergency key (kernel daemon, then a real-time thread) is never serviced → no thread runs.
- Found while looking: **GICv2 sent SGIs without a write barrier** (GICv3 has one; Linux does `dmb ishst`):
  an ICI could overtake its message → sender spins forever. Fixed (in bench).
- emmc2 shares GIC SPI 126 with the legacy SDHCI at 0x7e300000 (WiFi SDIO, no Haiku driver): an
  interrupt storm from it would freeze a CPU exactly like this. Diagnostic counter in the sdhci handler
  (bench `storm`).
- USB: PCIe root complex driver `busses/pci/brcmstb` written from `docs/design/brcmstb-pcie.md` (agent
  research: U-Boot tears PCIe down at ExitBootServices → full init + VL805 firmware via mailbox); USB
  DMA memory below 3 GiB + non-cacheable on arm64. Compiles; stashed (`pcie-usb-wip`) until the freeze
  is understood, then first HW test.

### 2026-10-18 (03:45) — boot freeze: gone empirically (8/8)

### 2026-10-18 (06:15) — **WiFi stages 0 + (a): SDIO works on the Pi 4** (H11)
- Design: `docs/design/wifi-bcm43455.md` (port OpenBSD `bwfm` onto `openbsd_wlan`, real SDIO in the mmc
  bus manager).
- sdhci_fdt attaches the legacy Arasan (`brcm,bcm2835-mmc`, mmcnr @0xfe300000) with its quirks: EMMC
  firmware clock (250 MHz), no HISPD bit, PIO, **3.3 V although its caps report no voltage** (else it never
  powered up: "No voltage is supported", CMD0 never completed). Shared GIC SPI with emmc2: claim only
  signalled bits. WL_REG_ON power-cycle at attach via the firmware GPIO expander (line 129).
- mmc bus manager: CMD5 probe → OCR → RCA → CCCR/CIS → `SDIO card 02d0:a9a6, 3 functions`; 4-bit, high
  speed timing, 25 MHz; device-interface SDIO ops (CMD52, CMD53 block+byte mode, block size, function
  enable). SD boot unaffected (memory card re-reset after the CMD5 probe, so its first R1 is clean).
- Bring-up findings: (1) Arasan loses a write to the same 32-bit register within 2 SD clocks → block
  size + count written as ONE 32-bit word (Linux shadows them too); (2) backplane reads hung until
  `CHIPCLKCSR = FORCE_HW_CLKREQ_OFF | FORCE_ALP` (Linux's second write) — with HW clock requests off,
  ALP must be forced; (3) multi-block reads of **chipcommon registers** CRC-fail — a test artefact, RAM is
  fine; (4) firmware SET_GPIO_STATE doesn't mark its tag response — accept like Linux.
- **Exit met: chip BCM4345 rev 6 (43455c0); 4 KB block-mode write + read-back of SOCRAM 0x198000 matches.**
