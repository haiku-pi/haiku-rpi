  efi_alloc() zeroes, the direct callers do not.

### 2026-11-02 (11:01) — The reader: the kernel's empty TTBR0 table is never cleared (one cause for both pages)
- Code analysis (agent, read-only): `sEmptyTable` (kernel/arch/arm64/arch_vm_translation_map.cpp:87) comes from
  vm_allocate_early_physical_page(), which does not clear, and is installed as TTBR0_EL1 for every kernel-only
  thread (arch_vm_install_empty_table_ttbr0, SwitchUserMap); TCR_EL1.EPD0 is never set, so the walker uses it
  (speculatively too). Its garbage entries map random physical memory. It is the kernel's first early page = the
  first page above the loader's LoaderData ranges: the loader's PE header page on an SD boot, the U-Boot pool page
  between the loader's data and its image on a network boot — exactly the two pages bisected. Upstream regression:
  593f25d6f1e (2026-03-17, "arm64: Fixes for booting in EL2 w/ E2H") moved it from vm_page_allocate_page(...,
  VM_PAGE_ALLOC_CLEAR) to the early allocator.
- Fix (uncommitted until the Pi test): memset the page through KERNEL_PMAP_BASE + dsb ish (+ a temporary dprintf of
  its address). Test queued after the cold network series (q9): that kernel with the OLD loader (f593b2ae43 backed
  out for the build only, re-applied) and the random-fill U-Boot without 0004/0005 — the setup that froze 3 of 3 —
  3 warm SD boots; the dprintf should print 0x39e3a000.
- Cold network series (U-Boot 0001-0005): round 1 alive.
