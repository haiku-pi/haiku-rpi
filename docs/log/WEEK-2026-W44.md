### 2026-10-29 (10:03) — **W8 fixed on the host: Wine 0026, wine 11.20-21** (agent; Pi check pending)
- Cause: `cancel_process_async()` (server/async.c:685, NtCancelIoFile/NtCancelIoFileEx) cancels an async, then
  attaches the cancel object and moves it to its tracked list **without a reference of its own**. When the
  completion APC cannot be queued, `cancel_async()` → `fd_cancel_async()` → `async_terminate()` →
  `thread_queue_apc()` fails → the APC's destroy → `async_set_result()` drops the queue's reference — for an
  overlapped read the last one: the async is freed inside `cancel_async()`, then written to and linked back
  into `process->asyncs`; its memory comes back as the next async → the two-entry cycle of the core
  (cancel_terminating_thread_asyncs() then spins). CancelIo's variant also never signals the cancel object
  (count++ after the completion): the cancelling thread waits for ever.
- Why Haiku (on Linux only when no thread of the process can take the APC): the server cannot signal a thread
  there (ntdll sends no Unix thread ID, `unix_tid` = -1, so `send_thread_signal()` always fails): the APC fails
  whenever the thread is not waiting — CancelIo() by the reader every time; CancelIoEx (rpcrt4, services.exe)
  when the reader is not waiting yet.
- Host proof: `scripts/build-wineserver-host.sh` (new: the patched tree's wineserver for x86-64 Linux with ASan,
  run under the reference Wine; `HAIKU_SIGNALS=1`: send_thread_signal() fails as on Haiku). **The wineboot loop

### 2026-10-29 (16:47) — **Scheduler fix: two busy threads stuck on one core while three idle** (haiku 2486477fab)
- The slow flushwb-arm64 (412-474 s for 100,000 rounds, sometimes 1 s) was not Wine's: `ps -a` during a slow run
  showed one litmus thread `run`, the other `rdy` — both on one core, the other three idle, for minutes. Native
  repro with `tools/haiku-tests/spread.c` (two unpinned threads at a spinning barrier): a process's first pair
  stuck at the quantum (3.8-4.7 ms/round, cut short at 10 s) in 10 of 10 runs on image-2026-10-29c.
- Cause: a thread that always runs needs kMaxLoad (its needed load is measured against the time it was
  available, which does not grow while it waits ready). Two on one core make the core's load 2000, but
  `CoreEntry::GetLoad()` caps it at 1000: low_latency's `rebalance()` saw 1000 − 0 − 200 = 800 against an idle
  core, less than either thread's 1000, so neither ever moved. Multi-CPU (SMT) cores escape (the thread load is
  divided by the CPU count); every single-CPU-core machine (arm64 boards, x86 without SMT) has it — a general
  Haiku scheduler bug, not a Wine or test artifact. It strikes when both threads land on one core at creation
  before their loads build up.
- **haiku rpi4 2486477fab**: `rebalance()` compares the core's uncapped load (`CoreEntry::GetUncappedLoad()`).
  Pi A/B (network sessions, 10 runs each): 29c 10/10 stuck → fixed 0/10, 0.19-0.22 µs/round; busy 1-4 threads
  unchanged; release-check 0 problems (Firefox 7.7 / 3.1 / 3.1 s, GLTeapot 107/58 ms, 24 launch cycles).
  power_saving's `rebalance()` has the same shape (named in the commit, not changed: not the default mode).
- HAIKU-RPI4-CHANGES: rows for 2486477fab, 1582c223b0 (team memory barrier), 8a65ea1c6d (Debugger CLI).
