### 2026-10-19 (00:30) — boot freeze: an SPI left active on CPU 0; a watchdog recovers it (10/10)
- A watchdog on every CPU (`arch_int_gicv2.cpp`, 5b2e85f498) checks the others every 250 ms: a CPU with
  an overdue timer event that took no interrupt is reported and sent an SGI. It caught one:
  `CPU 0 has a timer event 396416 us overdue, last interrupt 158 … SPI pending … 0x40000000, active …
  0x40000000; sending it an SGI` → `CPU 0 took interrupt 27 5 us after the SGI`.
- **Mechanism**: SPI 158 (the two SDHCIs' shared interrupt) stays *active* on CPU 0 after its handler,
  i.e. its end of interrupt has not taken effect; CPU 0 then takes nothing of that priority (its timer, the
  SD completion) while it sleeps, until another CPU accesses the GIC (the UART's interrupt did that
  before, after ~75 s). Root cause open (why the EOI does not take effect; a read-back after EOIR did not
  cure it).
- Bench with the watchdog: **10/10** (one freeze recovered after 0.4 s), was ~50 % frozen. Kept also:
  `dsb sy` before `wfi`. The freeze probe is gone; `boot-bench.sh` no longer types Ctrl-T (it hid freezes)
  and counts watchdog recoveries per trial.
- Refuted on the way: a lost synchronous ICI (a detector never fired), the boot-time page table, the
  firmware overlay.

### 2026-10-19 (01:20) — GPU stage 4a: `bcm2711_display` driver + accelerant (retrace 60.00 Hz)
- New kernel driver `drivers/graphics/bcm2711_display` + `bcm2711_display.accelerant` (haiku c9b4bfe234),
  forked from the framebuffer driver: adopts the boot framebuffer (write-combining), the monitor's EDID
  from the firmware (`GET_EDID_BLOCK`), and a **retrace semaphore**. app_server prefers it over
  `framebuffer` (its first scan skips vesa/framebuffer); desktop and windowed GL (750 fps) work on it.
- Vertical blank: the firmware raises **no SMI interrupt** without its firmware-KMS DT node (`firmwarekms`
  is disabled in the stock DTB; Phoenix's 60.01 Hz SMI ran with the fkms overlay), so the driver falls back
  to a thread on the blocking `SET_VSYNC` call: `retrace` (BScreen::WaitForRetrace) **60.00 Hz, gaps
  16655-16677 us** — stage 4's retrace exit criterion. The thread holds the mailbox ~16 ms per call (other
  mailbox users wait up to a frame). **With `firmwarekms` enabled** (new `tools/overlays/haiku-fkms.dts`,
  now the image default; it leaves `/soc/fb` alone) the firmware raises the **SMI interrupt (144)**:
  60.00 Hz, gaps 16659-16668 us, framebuffer/desktop/GL unaffected.
- Lesson: a userland team may not acquire a kernel-owned semaphore (`B_NOT_ALLOWED`): the vblank semaphore
  belongs to the team that opens the device (app_server), as intel_extreme does.

### 2026-10-19 (21:30) — **the CPU stall root-caused: an LL/SC livelock in kernel spin-waits**, not the GIC
- Routing SPI 158 to CPU 1 moved its stalls there, and CPU 0 kept stalling after SGIs, V3D and its own
  timer: any CPU, any interrupt. Without the SGI the stall still ended 1–3 µs after another CPU's
  *check*; a passive check (no stores) saw ~400 stalls of up to 760 ms in 10 minutes. The stalled CPU's
  own view at the end: **CNTV_CTL 0x5 — the timer had fired on time; interrupts were masked**.
- Where (ELR at the interrupt that ended it, addr2line): the pair was CPU 0 in the SD interrupt (hence
  158 "active": no EOI yet) notifying a condition variable, spinning in `_NotifyLocked()` on
  `fEntriesCount`, and the waiter (`mmc storage scheduler`) in `ConditionVariableEntry::_RemoveFromVariable()`,
  both with interrupts disabled. The Cortex-A72 has no LSE atomics, so `atomic_add`/`atomic_get_and_set`
  are load/store-exclusive loops; the notifier's tight `ldar` polling of the cache line that also holds
  `fLock` and `fEntriesCount` keeps clearing the waiter's exclusive monitor, its store-exclusive keeps
  failing (plus `try_acquire_spinlock()` exchanging on that line even when it was held). It ends when
  timing shifts — any other CPU's access to the line or the GIC did it (the old "freeze ends when the UART
  interrupt comes"; the watchdog's "SGI" fix).
- Fix (haiku 0db3ca639d, Linux's way): on arm64 `cpu_wait()` sleeps in **WFE** on the line (`ldxr` + `wfe`, as
  `__cmpwait()`), the generic timer's **event stream** (every 152 µs) bounds every WFE, and
  `try_acquire_spinlock()` tests before it exchanges. Kept too: an ISB after the timer register writes
  (architecturally required, as Linux), and the Linux GIC setup. **The GIC watchdog and all stall
  diagnostics are removed.** 10-minute soak with the fix and a passive checker: no livelock stalls left
  (the only interrupts-off spans >10 ms are the synchronous serial `dprintf`s of the test itself).
- **Boot bench 10/10 without the watchdog** (before the watchdog, about half of all boots froze).

### 2026-10-20 (06:30) — **C++ exceptions were broken in cross-built ports** (toolchain); SuperTuxKart built
- Found by the SuperTuxKart port (agent), confirmed in the gcc specs: the arm64 cross g++ links only the static
  libgcc (`*libgcc: -lgcc`), because `USE_LD_AS_NEEDED` follows a configure probe that fails while a cross gcc is
  configured before its binutils exist. A program's unwind tables then register with that private unwinder, and
  libstdc++'s (libgcc_s) never sees them: **every `throw` ends in `terminate()`** — even `throw 42` in main.
  Haiku's own binaries are fine (jam links `libgcc_s` explicitly: libbe, Tracker, app_server checked); only ports

### 2026-10-22 (03:00) — H15: why emulated full screen is stretched
- `+waylanddrv` on ddtest 640x480: the game window is first placed 4:3 ((240,0)-(1680,1080): 1440x1080), then
  made full screen — win32u gives the driver the whole monitor ((0,0)-(1920,1080)) for the emulated 640x480

### 2026-10-22 (03:20) — H15: the full-screen picture's mechanism, end to end

  (1440x1080), and a decision for emulated modes whose aspect differs from the screen's: stretch to the
  screen, or letterbox (keep 4:3 centered) — letterboxing keeps games right.
