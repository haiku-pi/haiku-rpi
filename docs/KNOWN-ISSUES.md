# Known open issues

Every issue we know about and have **not** fixed, in one short register.

- **Open only.** A fixed issue leaves this file once the newest release image (or a published package)
  carries the fix; until then its row says where the fix is. Its story stays in the weekly log ([log/](log/)),
  where each row below points ("tracked").
- **Short.** Each row says what is wrong, how often, the workaround, and where it is tracked. Measurements
  and investigations live in the log entries named.
- What works and how well: [HARDWARE-SUPPORT.md](HARDWARE-SUPPORT.md). The bench the rates were measured
  on: [LAB-SETUP.md](LAB-SETUP.md).

Checked against the weekly logs up to **2026-11-05 02:21** (the newest entry: 2026-11-05 01:49).

| C13 | **Images up to image-2026-11-04 corrupt data on USB disks — fixed in image-2026-11-04b; update.** The xHCI driver did no cache maintenance for USB disk transfers and the Pi 4's USB controller does not see the CPU caches, so reads returned stale data and writes stored stale memory, on any USB disk and without an error in the log (the bench stick itself is fine: Linux on the same Pi reads and writes it correctly). ## 2. Graphics and UI

| # | Issue | How often | Workaround | Tracked |
|---|---|---|---|---|
| G2 | **Firefox drops video frames in the first seconds after it starts.** On image-2026-11-05b the first 720p clip after Firefox starts loses **30–93 of 300** frames on a network boot (median 48; 46–56 when Firefox is restarted with every file already in memory) and **9–21 from the SD card**; the same clip again loses 0–20, and **none if it starts 30 s after the window opens**. H.264 and VP9 behave the same. Every lost frame is dropped by Firefox's video sink because it arrived late; the decoder skips none. Cause: Firefox's own start-up work (5–7 s of main-thread CPU, one or two content processes started, workers, database threads; more when online) competing for the four cores with video drawn in software (about one CPU for 720p); two busy loops cause the same drops on a settled Firefox. Not disk I/O, the decoder, audio or GL; the 1.8 s decoder stalls of W43 are gone ([design/perf-round-h20.md](design/perf-round-h20.md) "C6 / G2 results"). | First 10–15 s after Firefox starts | Wait ~30 s, or play the clip again; `dom.ipc.processPrelaunch.enabled` and `browser.newtab.preload` set to false in `user.js` halve it (new tabs then start their content process on demand — not shipped by default) | W43: 10-20 18:20, 19:40; 10-21 01:00; W44: 10-29 19:20; W45: 11-05 |
